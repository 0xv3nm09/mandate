# PayPal integration — every call, payload, and real response

The complete map of how Mandate talks to PayPal: authentication, Invoicing v2, Payouts v1,
webhooks, the official agent toolkit, and the exact errors we hit on the live sandbox with
how each is handled. Every request body below is the literal shape the gateway sends
([`server/src/paypal/gateway.ts`](../server/src/paypal/gateway.ts)); every response excerpt is
from a real run captured in [`evidence/`](../evidence/).

Base URL: `https://api-m.sandbox.paypal.com` (env: `PAYPAL_BASE`).

---

## 1. Authentication — OAuth 2.0 client credentials

```
POST /v1/oauth2/token
Authorization: Basic base64(PAYPAL_CLIENT_ID:PAYPAL_CLIENT_SECRET)
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
```

Real response shape:

```json
{ "scope": "...", "access_token": "A21A…", "token_type": "Bearer", "expires_in": 32400 }
```

**Handling:** the gateway caches the token and re-mints ~60 s before expiry
(`getAccessToken()`), so no request in flight ever carries a stale token.

## 2. Invoicing v2 — money-in (autonomous by policy)

### 2.1 Create draft invoice

```
POST /v2/invoicing/invoices
Prefer: return=representation
PayPal-Request-Id: mandate-invoice-<actionId>        ← 1-hour idempotency (docs)
```

Request body (literal):

```json
{
  "detail": {
    "invoice_number": "MANDATE-<base36-ts>",
    "currency_code": "USD",
    "note": "<memo from the NL instruction>",
    "terms_and_conditions": "Generated by Mandate — governed by a signed Intent Mandate."
  },
  "invoicer": { "business_name": "Mandate Demo Merchant", "email_address": "merchant@mandate.demo" },
  "primary_recipients": [
    { "billing_info": { "email_address": "<recipient>", "name": { "full_name": "<payee name>" } } }
  ],
  "items": [
    { "name": "<memo>", "quantity": "1", "unit_amount": { "currency_code": "USD", "value": "1200.00" } }
  ]
}
```

**Two response shapes exist (a real gotcha):** with `Prefer: return=representation` the
201 returns the full invoice body (`{ "id": "INV2-…", "status": "DRAFT", … }`). Without it,
the sandbox returns a **bare HAL self-link**:

```json
{ "rel": "self", "href": "https://api.sandbox.paypal.com/v2/invoicing/invoices/INV2-A8XV-ZMVP-3TV8-R95A", "method": "GET" }
```

The gateway parses **both** (`id` field, or last path segment of `href`). Real ids created
this way: `INV2-A8XV-ZMVP-3TV8-R95A`, `INV2-5NJY-663X-87H4-V2YA` (see
[`evidence/usecases/UC-01.json`](../evidence/usecases/UC-01.json)).

### 2.2 Send invoice

```
POST /v2/invoicing/invoices/{invoice_id}/send
{ "send_to_invoicer": false, "send_to_recipient": true }
```

202 Accepted on success. **The sandbox 422 (`USER_NOT_FOUND`) if the recipient email is not
a real sandbox personal account** — Mandate routes around this with
`PAYPAL_SANDBOX_RECIPIENT` (invoices go to the configured test account; the ledger keeps the
logical payee) and degrades gracefully: status `CREATED` (a real PayPal draft) + a
`POST /api/invoices/:id/resend` recovery route.

### 2.3 Remind (AI-drafted, tone-escalating)

```
POST /v2/invoicing/invoices/{invoice_id}/remind
{ "subject": "<AI-drafted subject>", "note": "<AI-drafted body>", "send_to_invoicer": false, "send_to_recipient": true }
```

204 on success. **Hard limit from the docs: 2 reminders per invoice per day** — a 422 here is
caught, audited as `SYSTEM`, and surfaced as "rejected — daily cap; try again tomorrow"
instead of failing the flow.

### 2.4 Native auto reminders (one-time setup)

```
POST /v2/invoicing/setup-reminders
{
  "configurations": [
    { "type": "BEFORE_DUE", "interval": { "unit": "DAY", "value": 2 }, "repetition": 1, "notification": { "send_to_invoicer": false } },
    { "type": "AFTER_DUE",  "interval": { "unit": "DAY", "value": 2 }, "repetition": 2, "notification": { "send_to_invoicer": false } }
  ]
}
```

Configured best-effort on the first invoice (PayPal's own reminder engine now runs *alongside*
our AI reminders). A 422 ("already configured") is tolerated and audited.

## 3. Payouts v1 — money-out (the governed path)

### 3.1 Create payout batch

```
POST /v1/payments/payouts
```

Request body (literal — the `sender_batch_id` **is** our idempotency key):

```json
{
  "sender_batch_header": {
    "sender_batch_id": "approval:mw6whx2612fa58",
    "email_subject": "You have a payout from Mandate"
  },
  "items": [
    {
      "recipient_type": "EMAIL",
      "amount": { "value": "500.00", "currency": "USD" },
      "receiver": "<recipient>",
      "note": "<memo>"
    }
  ]
}
```

Three key namespaces for `sender_batch_id`:

| Key | Meaning | Who authorized |
| --- | --- | --- |
| `approval:<id>` | a gated payout after the human tap | operator (one tap) |
| `standing:<payee>:<isoWeek>` | a pre-authorized weekly run | the signed mandate envelope |
| `governed:<actionId>` | any other in-bounds execution | the policy engine |

Real response excerpt:

```json
{ "batch_header": { "payout_batch_id": "ZCWVF6MKS57FG", "batch_status": "PENDING" } }
```

Real batches (see [`evidence/paypal-payouts.json`](../evidence/paypal-payouts.json)):
`CM9XMWV3ZZYFC` → **SUCCESS** (funds settled between sandbox accounts) ·
`ZCWVF6MKS57FG` → PROCESSING.

### 3.2 Duplicate `sender_batch_id` — PayPal's idempotency, honored

After a local ledger reset, re-running a same-week standing payout returns:

```json
HTTP 400
{ "name": "USER_BUSINESS_ERROR",
  "details": [{ "field": "SENDER_BATCH_ID", "issue": "Batch with given sender_batch_id already exists",
                "link": [{ "href": "…/v1/payments/payouts/CM9XMWV3ZZYFC", "rel": "self" }] }] }
```

Mandate treats this exact 400 as an **idempotent no-op**: the action is marked EXECUTED, the
audit records `moneyOut: 0` with `duplicateOf: <batch>`, and no double-pay can occur. Every
other gateway error marks the action FAILED and surfaces (retry/backoff → queue, never
silent-execute).

### 3.3 Batch status

```
GET /v1/payments/payouts/{payout_batch_id}   →   batch_header.batch_status
```

Sandbox batches settle **asynchronously** (minutes) — UC-12 polls this live instead of
trusting the local cache, which is how `CM9XMWV3ZZYFC` was observed flipping to SUCCESS.

## 4. Webhooks

Inbound: `POST /api/paypal/webhook` (our endpoint). Events handled:

| Event | Effect |
| --- | --- |
| `INVOICING.INVOICE.PAID` | invoice → PAID, audit `WEBHOOK` record, SSE to the console |
| `PAYMENT.PAYOUTS.EVENT` | payout status updated (e.g. → SUCCESS), audited |

**Verification (sandbox with `PAYPAL_WEBHOOK_ID`):** every inbound event is verified via

```
POST /v1/notifications/verify-webhook-signature
{ "transmission_id": "…", "transmission_time": "…", "cert_url": "…", "auth_algo": "…",
  "transmission_sig": "…", "webhook_id": "…", "webhook_event": { … } }
```

→ `{ "verification_status": "SUCCESS" }` required, else the event is rejected (403). All
events are additionally deduped by event id (replay-safe).

**Deterministic demos:** `POST /v1/notifications/simulate-event` with
`{ "webhook_id": "…", "event_type": "INVOICING.INVOICE.PAID" }` fires any webhook on demand
(exposed as `POST /api/paypal/simulate-event` in sandbox mode).

## 5. Official agent toolkit — read-only eyes

```ts
new PayPalAgentToolkit({
  clientId, clientSecret,
  configuration: {
    actions: { invoices: { list: true, get: true }, disputes: { list: true, get: true } },
    context: { sandbox: true },   // required — the constructor throws without it
  },
}).getTools()  →  list_invoices · get_invoice · list_disputes · get_dispute
```

Filtered to `/^(list|get)_/` — **read-only**. These tools go straight to the model (they move
no money); everything money-moving runs through the control plane instead. The toolkit
exposes **no Payouts tools** at all, which is exactly why Payouts go through documented REST
above. Live status: `GET /api/paypal/toolkit` → `{ available: true, toolNames: [ … ] }`
(captured in [`evidence/paypal-toolkit.json`](../evidence/paypal-toolkit.json)).

## 6. Gateway architecture — one interface, two implementations

| | `SANDBOX` (keys set) | `MOCK` (zero keys) |
| --- | --- | --- |
| createInvoice / send / remind | real REST above | stateful fake, same semantics |
| createPayout / status | real REST, idempotency keys honored | PENDING → SUCCESS, emits the same webhook event |
| verifyWebhook | `verify-webhook-signature` | accepts its own events |
| simulateEvent | docs endpoint | internal emission |

The control plane never knows which implementation is live — the entire trust layer is
identical in both modes, which is why CI runs the full suite offline and judges can run the
whole product with zero credentials.

## 7. Error catalog — real responses and handling

| # | HTTP | PayPal error | Trigger | Mandate's handling |
| --- | --- | --- | --- | --- |
| 1 | 404 | `RESOURCE_NOT_FOUND` on `/invoices/undefined/send` | create returned HAL link, client read `body.id` | parse `href` + `Prefer: return=representation` (§2.1) |
| 2 | 422 | `USER_NOT_FOUND` on send | recipient not a sandbox personal account | `PAYPAL_SANDBOX_RECIPIENT` routing + graceful `CREATED` + resend route (§2.2) |
| 3 | 400 | `Batch with given sender_batch_id already exists` | local reset vs PayPal's longer retention | idempotent no-op, audited `duplicateOf` (§3.2) |
| 4 | 422 | reminder rejected | >2 reminders/invoice/day | caught, audited, surfaced honestly (§2.3) |
| 5 | 5xx / timeout | — | transient | retry ×2 with backoff → queue; action stays PENDING, never silent-executes |

---

## 8. What we did NOT use (and why)

- **`@paypal/agent-toolkit` for money movement** — its tools execute PayPal calls directly
  from the model; that is the access-control boundary this project exists to remove. Read-only
  eyes only (§5).
- **MCP server (`mcp.sandbox.paypal.com`)** — designed for coding-agent workflows, not a
  runtime trust layer; the toolkit's AI-SDK surface is the right integration for this
  architecture.
- **Orders v2 / capture** — kept as the documented fallback if Payouts were ever unavailable
  for a gated money-out; not needed (Payouts verified live).
